# 管理主动任务

用户要求持续跟进或定时完成一项工作时，先用 `manage_proactive_agent(action="list")` 查找相关任务，按需用 `status`
核对现有设置。复用能满足要求的任务。每个后台任务对应一个具名 Proactive Runtime，创建、更新和删除均通过同一个管理接口写入工作区。工具参数放在顶层，用
`agent_name` 指定 Runtime。新名称用下划线连接简短的小写英文单词，忽略大小写必须唯一。避开框架为主对话保留的名称
`Remy`。

## 选择触发方式

- **事件触发。** 有新资料时处理，创建时省略 `cron`。 来源和采集方式明确时，让采集器持续保存新资料，通过 `append_task_events`
  投递事件，任务分批消费。例如实验日志更新时检查异常。采集器本身可以定时运行。
- **时间触发。** 到了约定时间再做，创建时填写 `cron`。 到点后由任务按要求取资料、完成工作并按需汇报。例如每天 8 点检索新闻并发送
  AI 日报。`cron`
  使用应用时区。
- **任务创建后类型固定。** 同一件事需要两种触发时，分别创建任务。 例如一个任务收到日志就检查异常，另一个任务每天 18 点汇总进展。

## 写任务要求并创建

把用户的目标、必要背景、资料来源、判断标准和提醒要求写成 `task_description`。创建时正文保存到 `task_path` 指向的 `TASK.md`
，任务每轮都会读取。本轮资料随观察事件提供，定时事件提供计划时间。触发日程写在 `cron`，资料时间范围和是否每轮发送写在任务要求里。

**每天早上 8 点整理并发送 AI 日报**

```json
{
  "action": "create",
  "agent_name": "ai_briefing",
  "cron": "0 8 * * *",
  "task_description": "时间触发时，以本轮计划时间为截止点，用 Web Search 检索此前 24 小时的重要 AI 新闻。核实原始来源，简洁说明事实和影响，附来源链接。每轮整理好后发送日报。"
}
```

**跟进实验，异常或结束时提醒**

```json
{
  "action": "create",
  "agent_name": "experiment_watch",
  "task_description": "收到实验日志时，读取本轮事件引用的文件。日志明确显示进程因错误退出、关键指标出现 NaN 或实验完成时提醒，说明状态和判断依据，并附原日志链接。正常进展只记录。"
}
```

如果还需要每天 18 点汇报实验进展，另建一个时间触发任务，设置 `cron="0 18 * * *"`，在任务要求中引用实验记录。

创建后核对 `task_path` 和实际任务要求。时间触发任务要核对 `next_trigger_at`。事件触发任务要完成采集接入。

## 接入观察并核对结果

1. 确认资料来源和采集宿主，优先复用现有采集器。用当前服务的 `POST /get_client_info`（请求体 `{}`）确认 `workspace_dir` 和
   `resource_dir`。在实际宿主配置并启动采集，留下运行入口和停止方式。
2. 先将原始资料完整保存到工作区，再向 `POST /append_task_events` 投递简述和文件路径。`task_names` 填目标任务名单，`paths`
   使用规范的工作区相对路径。
   `source="cron"` 由框架保留。

```json
{
  "task_names": [
    "experiment_watch"
  ],
  "events": [
    {
      "id": "experiment-log-snapshot-001",
      "event_ts": "2026-11-22T10:30:00+08:00",
      "source": "experiment_log",
      "description": "实验日志快照已更新。",
      "paths": [
        "resource/experiments/snapshot-001.log"
      ]
    }
  ]
}
```

用真实资料验证投递。核对 `answer.deliveries` 中各目标的事件 ID，并记录 `answer.rejected` 中的拒绝原因，例如目标已删除、属于时间触发，或事件
ID 冲突。
仅对 `answer.errors` 中的目标有限重试，复用原事件 ID 和内容。每个目标都完成投递或收到明确拒绝后推进采集游标。持续失败时让采集宿主报告错误。

用 `status` 的事件计数、`last_completed_at` 和 `error` 核对消费情况，再用 `query`
或每日记录核对分析。任务决定发送的提醒进入主对话的收件箱。实际提醒条件出现时核对发送结果。向用户汇报已经配置或验证到哪一步，以及还有哪一步待确认。

## 管理已有任务

| 用户想做什么       | 使用方式                                                                                                                                   |
|--------------------|--------------------------------------------------------------------------------------------------------------------------------------------|
| 查找任务或查看状态 | 用 `list` 查找，用 `status` 核对执行情况。`status=active` 表示执行中。                                                                     |
| 询问进展           | 有任务会话时用 `query`，传入 `question`。尚无会话时，查看状态和任务要求。                                                                  |
| 修改任务要求       | 读取 `task_path` 指向的 `TASK.md`，保留有效要求，保存后核对。通过 `task_document` 接口保存时，把读取返回的 `mtime` 传为 `expected_mtime`。 |
| 调整日程           | 时间触发任务可用 `update` 修改 `cron`。修改后核对 `next_trigger_at`。要改用事件触发时，创建新任务。                                        |
| 调整观察处理频率   | 对事件触发任务，用 `update` 修改 `min_trigger_interval_seconds`。间隔从上一轮成功完成时计。采集频率由采集器配置。                        |
| 调整提醒时段       | 用 `update` 设置 `notify_window`，传入 HH:MM 格式的 `{start,end}`，控制主对话自动处理和发送提醒的时段。传 `null` 取消限制。                |
| 暂停、恢复或删除   | 用 `update` 设置 `enabled=false` 或 `true`。用 `delete` 停止调度和执行并保留历史。暂停或结束监控时，按需停止该任务独占的采集作业。         |

同名恢复已删除的任务会沿用原触发类型、`TASK.md` 和历史。用户给了新要求时，恢复后核对并更新文件。
