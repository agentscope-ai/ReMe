# 环境管理

**Environment（环境管理）** 标签页用于在本机完成 ReMe 的准备工作：找到运行 DSH 那台机器上的 Python、把
`reme-ai[core]` 装进该解释器、写入 workspace 的 `.env`、并启动或停止本地 ReMe 服务——这些原本需要在多个终端里完成。

入口：**插件 → ReMe Bundle → reme-memory → 配置 → 环境管理**。

该标签页只管理**回环地址**（`http://127.0.0.1:…` 或 `http://localhost:…`）。服务地址为远程 URL 时，它只显示该地址是否可
用，并隐藏本地步骤。

页面上的所有结果都来自 DSH **Host**，而不是浏览器：Python 探测、文件读写、LLM 探测、服务健康检查都在 Host 上执行。因此即使
浏览器在另一台机器上，看到的也是 Host 的真实环境，顶部概览与服务卡片不会给出不一致的结论。

## 每一步做什么

| 分组        | 能力                                                                                                                                                 |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| 本地 Python | 探测 PEP 514 注册表、`py` 启动器、`PATH` 与 conda（base 与命名环境），标注来源和 `reme-ai` 状态，选择结果写入 `pythonPath`                           |
| ReMe 依赖   | 针对所选解释器检查 `reme-ai` 版本、`[core]` 附加依赖与 `reme` CLI；可选用软件源安装或升级 `reme-ai[core]`，显示实时日志并支持取消                    |
| ReMe 参数   | 编辑 workspace 的 `.env`；密钥只存在该文件中，界面仅显示掩码。保存要求 `EMBEDDING_API_KEY` 非空（关闭向量检索时用 `EMPTY`）。提供 LLM 连通性测试     |
| 服务控制    | 启动/停止本地 ReMe 服务，显示 PID、版本与日志；启动时注入 UTF-8 与 `NO_PROXY`、设置 `enable_logo=false`，并在 workspace 内运行以保证 `.env` 能被发现 |

顶部的概览区用三个标签（服务、Python、ReMe）概括同一份状态，并显示服务地址、探测时间与两个刷新操作。

## Python 探测

ReMe 需要 **Python 3.11 或更新版本**。标签页在 Host 上探测下列来源，只保留能通过验证片段（上报 `sys.executable`、
版本号与 base prefix 的 `-c` 探测）的解释器：

- Windows：PEP 514 注册表项（`HKLM`/`HKCU`）、`py` 启动器列表、`PATH`、`conda env list`。
- macOS / Linux：`PATH`（`which -a`）、常见的 `/usr/bin`、`/usr/local`、Homebrew（`/opt/homebrew`）、
  `~/.pyenv/shims` 与 `~/.local/bin` 路径，以及 `conda env list`。

`WindowsApps` 下的 Microsoft Store 占位符会被跳过，因为它们只是别名而不是解释器。装有 conda 时，命名环境会同时出现在
`conda env list` 与环境列表中，conda 根目录单独上报。

探测结果缓存 60 秒，点击概览区的**重新探测**会重新执行。推荐解释器按以下顺序选出：

1. 已安装受支持 `reme-ai` 的命名 conda 环境（排除 `base`）。
2. 其他已安装受支持 `reme-ai` 的解释器。
3. 任意命名 conda 环境（可直接安装 ReMe）。
4. 第一个可用解释器。

把鼠标悬停在**推荐**标签上可以看命中的是哪条规则。选择其它解释器只会写入 `pythonPath`；保持未选择则一直跟随推荐。列表默认
显示 6 行并可展开，支持按版本、来源、路径筛选。

## ReMe 依赖

检查会向所选解释器询问三件事，并以指标形式展示：

- `reme-ai` 元数据版本（`importlib.metadata.version("reme-ai")`），以及是否达到本集成要求的最低版本。
- `[core]` 附加依赖：`import agentscope` 是否可用。缺失时 `auto_memory` 与 `auto_dream` 不可用。
- `reme` CLI：解释器旁的命令行入口，或启动时回退使用的 Python 包装。

**安装 reme-ai[core]** 执行 `python -m pip install reme-ai[core]`，可附加软件源（PyPI、清华、阿里云）。**升级**追加
`-U`；**重装**追加 `--force-reinstall`，否则 pip 会把“存在但已损坏”的安装报成 “already satisfied”。首次使用需要下载较大的
依赖，视网络情况通常 5–20 分钟。

安装是 Host 侧的任务：

- 关闭配置页后仍在运行；重新打开标签页会为同一个解释器恢复进度。Host 按解释器查找正在运行的任务，所以两个解释器同时安装时，
  各自看到的是自己的进度。
- 进度按任务 ID 轮询，为另一个解释器发起的安装不会顶替当前显示；安装的响应也绑定在发起它的解释器上，切换解释器后迟到的响应会被丢弃。
- 安装成功后会自动重新检测 `reme-ai`（同一个解释器），依赖卡片与**启动服务**按钮随之更新，无需手动点“检测”。
- **取消**会同时终止 pip 及其构建子进程，且在进程真正退出前该解释器保持占用。若进程不响应请求，会被强制结束；
  即便强制结束也未得到确认，任务仍保持“正在取消”状态、该解释器依然被占用——在第一个安装还没有交代清楚之前，
  不允许第二个安装开始。页面会继续显示该任务，而不是把它报告成一次已完成的取消。
- 日志写入 `$DSH_HOME/reme-memory/install-<job>.log`，页面直接显示尾部。每次安装都会新建文件，目录只保留最近
  20 个；长期运行的服务日志超过 5 MB 后轮转为 `service.log.1`。
- 插件卸载时，仍在运行的安装走同一条终止路径：先发优雅信号，再强制结束，因此忽略 `SIGTERM` 的 pip 不会比 Host
  活得更久。

## Workspace `.env`

ReMe 在服务启动时读取 workspace 目录下的 `.env`；标签页从不把密钥写进 DSH 设置。

| 分组      | 键                                                                                     |
| --------- | -------------------------------------------------------------------------------------- |
| LLM       | `LLM_BACKEND`、`LLM_MODEL_NAME`、`LLM_API_KEY`、`LLM_BASE_URL`                         |
| Embedding | `EMBEDDING_BACKEND`、`EMBEDDING_MODEL_NAME`、`EMBEDDING_API_KEY`、`EMBEDDING_BASE_URL` |

- workspace 目录默认 `~/.reme`，必须是绝对路径；修改后会重新读取它指向的 `.env`。
- API Key 是只写的：Host 只返回掩码（末四位），留空表示保留已存的值。没有编辑过的键不会被重写。
- 清空**密钥**字段并保存会保留已存的密钥——即便先输入过替代值再清空也是如此：凭据无法通过清空输入框来删除，
  因此留空始终表示“保留已存的值”。清空**非密钥**字段并保存即表示**删除**该值。只有编辑过的字段会被写入，
  文件其余部分的注释、未知键与顺序保持不变。
- 保存只清除本次提交的那部分编辑，更晚的编辑会被保留：保存进行中再改动其它字段时，那份文本不会丢失，页面也会
  提示仍有未保存的改动。
- 保存时会校验合并后的整份文件，而不只是本次输入：ReMe 0.4.0.x 会无条件实例化 embedding 组件，因此即使不使用向量检索
  `EMBEDDING_API_KEY` 也必须非空（`EMPTY` 是文档化的占位值）。重复出现的键会在每一处被改写，文件原有的换行风格也会保留。
- 写入是原子且仅属主可读写的（POSIX 上为 0600）；旧文件会保留为 `.env.bak`，因此一次失败的保存不会丢掉其它键。
- **测试 LLM 连接**在 workspace 内、用所选解释器发送一次只需 1 个 token 的请求，并对 `401`/`403`
  （密钥）、`404`（模型名或 Base URL）与网络错误给出提示。请求按 `.env` 里的 `LLM_BACKEND` 选择协议：
  `openai`、`dashscope`、`deepseek`、`moonshot` 走 OpenAI 兼容的 `/chat/completions`（Bearer 认证），
  `anthropic` 走 `/v1/messages`（`x-api-key`），`gemini` 走 `/v1beta/models/<model>:generateContent`
  （`x-goog-api-key`），`ollama` 走 `/api/chat`（本地服务无需密钥），`xai` 走 `api.x.ai` 上 OpenAI 兼容的
  `/chat/completions`。
- Base URL 的来源与 ReMe 自身的凭据保持一致：`LLM_BASE_URL` 只对 OpenAI 兼容族与 Anthropic 生效，Gemini、Ollama
  与 xAI 自带地址、并不读取该变量。因此 `.env` 里残留的旧值不会把探测引到服务根本不会访问的主机，ReMe 能接受的
  配置也不会被报成故障。Base URL 的拼接方式与服务商 SDK 完全一致，因此已经带版本后缀的地址在探测与服务中都会
  同样失败。
- ReMe 通过 gRPC SDK 连接 xAI，因此 xAI 的探测只是该通道在 REST 层面的近似。
- 探测读取的是磁盘上的 `.env`，所以只在表单里改过配置而未保存时不会发起测试；等待期间按钮会给出提示。
- 草稿与输入它的 workspace 绑定：切换 workspace 会丢弃草稿，因此为某个 workspace 输入的密钥不会被保存到另一个。

## 连接测试

概览区的**测试连接**让 Host 对配置的服务地址执行 `POST /health_check`。健康响应必须包含可解析的 ReMe 健康报告——版本、
健康标记与各组件明细——所以只回 `200` 与 `{}` 的普通 HTTP 服务不会被当成运行中的 ReMe。Host 复用插件其余部分使用的
同一个 ReMe 客户端，因此请求、鉴权与三秒超时都与服务本身被调用时一致。设置里填了 `authToken` 时，Host 会以
`Authorization: Bearer` 发送，且只作用于该服务地址。

## 服务生命周期

在这里启动服务等价于在终端执行 `reme start`，但有一点是刻意的差异：**服务会比 DSH 活得更久**。关闭 DSH 不会停止它，停止
它是在标签页里的一次显式操作。

因此本插件没有把服务交给 DSH 的本地子进程提供方——后者会在 Host 退出时终止它托管的进程。插件自带一个小型服务适配器：

- 启动在操作系统确认 spawn 之后才记录到 `$DSH_HOME/reme-memory/service.json`（pid、地址、workspace、命令行、启动时间），
  所以解释器缺失时不会留下残留状态。
- 只有记录与当前地址一致、pid 仍存活、进程映像仍是 Python 或 `reme`，**且命令行仍包含记录的 `workspace_dir` 与
  `service.port`** 时，服务才被判定为“由本插件托管”并给出**停止**按钮。命令行能排除大多数 pid 复用（更长的
  workspace 路径、另一个端口都不会命中），但无法区分“用户照抄同一命令行手工启动”的同一服务。2333 端口上的记录绝不会
  声称管理 2444 端口上的服务。
- 证据读不到时（`tasklist`/`ps` 输出本地化、权限不足等）归属保持“未证明”：启动与停止都不会碰进程、也不会丢弃记录——
  停止会拒绝，启动会返回错误。丢弃记录会让一个仍在运行的进程变成标签页再也停不掉的孤儿；此时卡片会给出**忘记这条记录**，
  它只删除 `service.json`、绝不向进程发信号，由用户自行确认后续处理。Host 会在结果里指明挡住操作的是哪一条记录，
  **忘记**针对的正是那条记录（可能是另一个端口上的记录，而不是当前显示的地址），并带上它的 pid：记录在此期间被换掉时，
  Host 会拒绝而不是静默丢弃新记录。
- 服务占用端口但健康检查失败时显示为“端口被占用”；若能证明是本插件启动的，标签页仍给出**停止**按钮。
- **停止**会树杀记录的进程（POSIX 上按进程组、Windows 上为 `taskkill /T /F`），等待其退出，必要时升级（POSIX：
  `SIGTERM` 后 `SIGKILL`；Windows：再次强制 `taskkill`），并**在 pid 真正消失之后**才清除记录。别处启动的服务不受影响，
  只会被观察。
- 记录中的进程仍存活但从未就绪时，显示为**上次启动未就绪**，并同时给出**停止**与**启动**：停止负责清记录，启动则让 Host
  停掉可证明归属的旧启动、或丢弃已证明属于外部的记录。只有本标签页发起的启动仍在进行时才会显示“启动中”。
- **启动**是串行化的：两个请求不会拉起两个服务，后到的请求会观察已在进行的启动。替换“一直没有就绪”的旧记录时，只有
  归属被证明才会杀掉它；证明不了就保留记录并报错，不会静默丢弃。
- **自动启动**（`autoStart`，默认关闭）会在 DSH 启动时把尚未运行的服务拉起。

Python 探测与 pip 安装都是有界的 Host 操作；服务是唯一需要比 DSH 活得更久的进程。

## 平台支持

| 方面        | 说明                                                                                                                                                |
| ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| DSH         | `0.1.7-rc.2`、`0.2.0-rc.2`、`0.2.1-alpha.2`、`0.2.1-alpha.4`、`0.2.1-rc.2`、`0.2.2-alpha.2`                                                         |
| Node.js     | `^22.19.0` 或 `>=24.0.0`；当前 DSH 需要 Node 24.9 以上，兼容矩阵以 Node 24.16 验证                                                                  |
| Windows     | 在 Windows 11 + Miniconda 上实测：注册表/PATH/conda 探测、`tasklist`/`taskkill` 身份校验与停止、`PYTHONUTF8`/`PYTHONIOENCODING` 保证 pip 输出不乱码 |
| macOS/Linux | 探测、分离启动、身份查询与停止均有运行真实子进程的单元测试覆盖；真机验证程度仍低于 Windows                                                          |

## 常见问题

**未检测到可用的 Python。** 安装 Miniconda 或任意 Python 3.11+，再点**重新探测**。Store 占位符会被过滤，请安装真实的发行版
而不是 Store 别名。

**所选解释器不在列表里。** 标签页会用“不在探测结果中”标注它，但仍然使用它。重新探测，或改选探测到的解释器。

**安装失败。** 先看日志尾部：缺少 wheel、代理配置过期或网络受限通常都能看出来，可以换一个软件源。conda 环境里 `pip` 也可
用，但独立环境更能避免与其它项目的依赖冲突。

**保存 `.env` 被拒绝。** 保存后的文件中 `LLM_API_KEY` 与 `EMBEDDING_API_KEY` 都必须非空；关闭向量检索时 embedding 用
`EMPTY`。清空密钥字段不会写入文件，已存的密钥会被保留；而一个根本没有存过的必需键仍会让保存失败，文件保持原样。

**服务显示“端口被占用”。** 该端口被其它程序占用。请在服务地址（记忆设置）中换一个端口，或停止占用它的程序。

**服务迟迟未就绪。** 启动会轮询 120 秒；如果端口有响应但 `/health_check` 一直不通过，卡片会切到“端口被占用”状态，**停止**按钮
始终可用。用**查看日志**（workspace 下的 `service.log`）看启动过程——缺少 `reme-ai`、`.env` 不合法、端口冲突都会体现在那里。

**服务显示“上次启动未就绪”。** 本插件记录的进程仍存活，但一直没有通过 `/health_check`（例如启动途中 DSH 被关闭）。点**停止**
清掉它后重新启动。若 pid 已被其它程序复用，这条记录可证明属于外部：点**启动**会丢弃记录并拉起新服务。若完全无法验证身份，
点**忘记这条记录**——它只删除本插件的记录，不会碰进程。

**服务显示为外部启动。** 它不是由本插件启动的，因此只被观察而不被管理。若希望在标签页里管理，先在它自己的终端里停止，再从
这里启动。

**停止按钮不可用。** 运行中的服务不属于当前服务地址，或记录已丢失。从标签页重新启动一次即可纳入管理。

**LLM 测试失败。** 结果会区分 `401`/`403`（密钥）、`404`（模型名或 Base URL）与网络错误。探测读取的是 workspace 的
`.env`，所以请先保存再测试；探测协议也取自其中的 `LLM_BACKEND`：原生后端（Anthropic、Gemini、Ollama）用自己的协议
探测，不会被当成 OpenAI 兼容接口。

## 代码位置

```text
integrations/dsh/src/environment/
├── types.ts          浏览器安全的共享 RPC 类型
├── env-fields.ts     受管的 `.env` 键及其更新规则
├── dependency.ts     一个解释器能承载什么
├── endpoint-rules.ts 哪些服务地址可以作为本地服务管理
├── host/             探测、安装、服务适配器、manager、gateway
└── client/           标签页：每个步骤一个模块，以及文案与样式
```

只有 Host 模块会接触进程与文件；客户端只负责渲染 Host 返回的结果。
