# Proactive

`proactive_read` is ReMe's interface for reading proactive memory. It does not reanalyze daily notes or call an LLM. It
reads interest topics written by the independent proactive refresh flow:

```text
daily/<date>/interests.yaml
```

A host agent can use it to learn "what is worth proactive attention today," then decide whether to remind the user, ask
a follow-up question, recommend a next step, or produce a proactive insight.

Every topic and agenda item carries a `kind`, one of exactly four values — `reminder`, `follow_up`, `new_idea`, and
`interest_extend` (see "Proposal Kinds" below). All four stay at the level of a proposal: the refresh pipeline never
carries any of them out, it only records what is worth raising with the user.

`interests.yaml` is generated by the proactive refresh pipeline, scheduled by `proactive_refresh_cron` by default.
`proactive_read` only reads and exposes the result; Auto Dream is an independent daily-to-digest flow and does not read
or write proactive state.

## Configuration

The default configuration is in `reme/config/default.yaml`. It defines the same refresh steps twice: a local-only
one-shot job for maintenance and debugging, and the scheduled job that runs every day at 18:00 in the application
timezone:

```yaml
proactive_refresh:
  backend: base
  enable_serve: false
  steps: &proactive_refresh_steps
    - backend: proactive_extract_step
      file_catalog: proactive
      scan_days: 2
      carry_forward_days: 14
      max_carry_forward_topics: 20
      llm_timeout_seconds: 300
      max_chars_per_file: 60000
      max_total_chars: 300000
      profile_max_chars: 1500
      capability_max_chars: 1200
      extends_enabled: true
      reminders_enabled: true
      new_ideas_enabled: true
      max_follow_ups: 5
      max_extends: 5
      max_new_ideas: 3
      reminder_lead_days: 3
      resources_enabled: true
      resource_max_chars: 40000
      max_notice_reminders: 3
      refine_enabled: true
      refine_timeout_seconds: 150
    - backend: proactive_topics_step
      known_threshold: 0.85
      known_threshold_calibrated_for: text-embedding-v4@1024
      min_push_confidence: 0.5
      min_reminder_confidence: 0.3
      max_topics: 10
      schedule_retention_days: 180
      max_schedules: 80
      max_schedule_history: 8
    - backend: proactive_plan_step
      max_reminder_cards: 8
    - backend: proactive_agenda_step
      min_discovery_slots: 2
      redelivery_cooldown_days: 3
    - backend: proactive_finish_step
      file_catalog: proactive

proactive_refresh_cron:
  backend: cron
  cron: "0 18 * * *"
  steps: *proactive_refresh_steps
```

The anchor above is only a compact illustration; `default.yaml` spells out both step lists explicitly. The read job is:

```yaml
proactive_read:
  backend: base
  description: "Proactive: read daily/<date>/interests.yaml and expose the latest user-interest topics."
  parameters:
    type: object
    properties:
      date:
        type: string
        default: ""
      include_content:
        type: boolean
        default: true
      horizon_days:
        type: integer
        default: 1
      min_confidence:
        type: number
        default: 0.4
      include_delivered:
        type: boolean
        default: false
      delivery_cooldown_days:
        type: integer
        default: 3
  steps:
    - backend: proactive_step
      min_confidence: 0.4
      delivery_cooldown_days: 3
```

Parameters:

| Parameter         | Purpose                                                                                              |
|-------------------|------------------------------------------------------------------------------------------------------|
| `date`            | Date to read in `YYYY-MM-DD` format. When empty, use today in the application's timezone.            |
| `include_content` | Whether to return the raw YAML in the answer and metadata. Defaults to `true`.                       |
| `horizon_days`    | Read one day's exposure file, or use the truth source for a wider evidence horizon. Defaults to `1`. |
| `min_confidence`  | Minimum topic confidence to return. Defaults to `0.4`; legacy topics use `0.5`.                      |
| `include_delivered`    | Also return agenda items the host already reported as delivered. Defaults to `false` (withhold). |
| `delivery_cooldown_days` | Days an already-delivered item stays withheld; `0` withholds same-day deliveries only. Defaults to `3`. |

### Refresh cost, files, and opt-out

With no daily Markdown change, no new external notice, and no due schedule, refresh exits before calling an LLM and
does not create a new exposure file. When only the clock produced due reminders the chain still runs to completion with
zero LLM calls (`reminder_only=true`), so today's agenda gets its reminders. With changed material, stage-1 recall makes
one LLM call (at most one retry after an unusable reply) and stage 2 then makes one small call per kind that actually
produced candidates (at most four). If push candidates remain, planning makes one additional call; agenda generation
makes one more when there are multiple candidates. A refresh therefore makes at most nine LLM calls with the default
chain, and only stage 1 carries the material blob.

The refresh pipeline maintains the rebuildable `daily/_proactive.yaml` truth source (open topics, resolved tombstones,
the long-lived `schedules` registry, and the `deliveries` ledger), writes `daily/<date>/interests.yaml`, and advances
the independent `proactive` file catalog. Auto Dream does not read or write any of those proactive artifacts.

To disable automatic refresh, use an explicit application config that omits the `proactive_refresh_cron` job. Keep the
local-only `proactive_refresh` job if you still want on-demand maintenance. Because it has `enable_serve: false`, it is
not exposed through HTTP or MCP.

## Proposal Kinds

Extraction makes a single recall call and asks for one sectioned reply covering four kinds. Each has a distinct job and
each is optional: a round may produce any subset of them, including none.

| Kind              | Job                                                                              | Scenario card                    | Per-round cap                                                |
|-------------------|----------------------------------------------------------------------------------|----------------------------------|--------------------------------------------------------------|
| `reminder`        | The user's own plans and appointments, plus notices and key events from external sources that the user must be told about | `prepare_upcoming` | Uncapped; undated notices are bounded by `max_notice_reminders` (3) |
| `follow_up`       | Recent progress on something the user assigned but never closed, or keeps tracking | `resume_task` / `answer_pending` | `max_follow_ups` (5)                                          |
| `new_idea`        | Work the agent can delegate to the user, based on its own resources (data, skills, tools, APIs) | `propose_delegation`  | `max_new_ideas` (3)                                           |
| `interest_extend` | Refinements and extensions of the topics the user cares about (growing the wiki network) | `explore_interest`         | `max_extends` (5)                                             |

`reminder` outranks the other three: the agenda step **pins** due schedules to the top of today's agenda (nearest due
first), where they are never suppressed and never swapped out, while discovery items always keep their
`min_discovery_slots` (2) slots — so a fully booked day does not collapse into a plain calendar. Reminder candidates go
through a lower gate in the topics step (`min_reminder_confidence` 0.3) and are exempt from `min_confidence` in
`proactive_read`.

Reminders are computed against the real clock (the configured application timezone) rather than from today's daily note
alone: before any LLM decision, extraction scans the `schedules` registry and deterministically seeds the `overdue`,
`due_today`, `conflict`, and `due_soon` (within `reminder_lead_days`) triggers. External notices under
`resource/<date>/` travel the same clock path, so a new external source needs no change to the proactive chain.

## Input Contract

A current proactive-refresh file looks like this:

```yaml
version: 2
date: 2026-06-20
generated_at: 2026-06-20T18:00:00+08:00
push: true
topics:
  - id: baa88ad49cb2
    title: Quality regression in the memory retrieval pipeline
    reason: The user has recently made repeated changes to search, node_search, and dream integration.
    kind: follow_up
    confidence: 0.86
    first_seen: 2026-06-20
    last_evidence_at: 2026-06-20
    evidence: daily/2026-06-20/session.md
    paths:
      - daily/2026-06-20/session.md
agenda:
  - topic_id: baa88ad49cb2
    title: Quality regression in the memory retrieval pipeline
    scenario_type: resume_task
    opener: Review the latest retrieval regression before the next release.
    next_action: Compare the failing query against the previous index snapshot.
    preconditions: []
    delivery: in_conversation
    linked_memory: []
    order_reason: Recent evidence and a concrete next action.
suppressed: []
```

Current v2 topics include stable identity, kind, confidence, evidence dates, and source paths. The reader also accepts
legacy v1 files containing `title`, `reason`, `evidence`, `keywords`, and `paths`; missing v2 confidence falls back to
`0.5`.

## Return Value

When the file is read successfully, `proactive_step` returns `summary` and `topics` in the primary answer. When
`include_content=true`, the answer also contains `content`. The same result fields remain available in standard response
metadata:

| Field     | Description                                          |
|-----------|------------------------------------------------------|
| `date`    | The date actually read.                              |
| `path`    | `daily/<date>/interests.yaml`.                       |
| `topics`  | Parsed topic list.                                   |
| `content` | Raw YAML; returned only when `include_content=true`. |
| `skipped` | `true` when the file does not exist.                 |
| `error`   | Read or parse error.                                 |
| `summary` | Short summary.                                       |
| `agenda`  | Today's proactive agenda (optional, v2 files only).  |
| `delivered_ids` | Agenda ids withheld this round by the delivery cooldown (when `include_delivered=false`). |

When today's `interests.yaml` was produced by the proactive refresh chain with an agenda,
the answer also carries an `agenda` field: the ordered agenda items, each with `topic_id`,
`title`, `scenario_type`, `opener` (a natural conversation opener), `next_action` (the
minimal executable step), `preconditions`, `delivery`, `linked_memory` and `order_reason`.
Agenda items whose topic is resolved or below `min_confidence` are filtered out on read;
the field is absent when the file has no agenda.

When the file exists and parses successfully, the answer is structured data. For example:

```json
{
  "summary": "Read 1 proactive topic(s) from daily/2026-06-20/interests.yaml",
  "topics": [
    {
      "id": "baa88ad49cb2",
      "title": "Quality regression in the memory retrieval pipeline",
      "reason": "The user has recently made repeated changes to search, node_search, and dream integration.",
      "kind": "follow_up",
      "confidence": 0.86,
      "first_seen": "2026-06-20",
      "last_evidence_at": "2026-06-20",
      "evidence": "daily/2026-06-20/session.md",
      "paths": ["daily/2026-06-20/session.md"]
    }
  ],
  "agenda": [
    {
      "topic_id": "baa88ad49cb2",
      "title": "Quality regression in the memory retrieval pipeline",
      "scenario_type": "resume_task",
      "opener": "Review the latest retrieval regression before the next release.",
      "next_action": "Compare the failing query against the previous index snapshot.",
      "preconditions": [],
      "delivery": "in_conversation",
      "linked_memory": [],
      "order_reason": "Recent evidence and a concrete next action."
    }
  ],
  "content": "date: 2026-06-20\n..."
}
```

With `include_content=false`, the `content` field is omitted from the answer. Missing-file and read-error answers remain
explicit `Skipped: ...` and `Error: ...` messages, respectively.

A missing file is not an error. The call succeeds with a skipped result:

```text
Skipped: interests file not found at daily/2026-06-20/interests.yaml
```

This lets a host agent treat "there is no proactive refresh result for today yet" as a normal empty state.

## Delivery Receipts

Refresh only decides what is worth raising; it cannot know what the host actually raised. `proactive_feedback` closes
that loop so an item the consumer already showed is not proposed again tomorrow:

```bash
reme proactive_feedback date=2026-06-22 items='[{"topic_id":"<id>","status":"shown","channel":"inbox","consumer":"<host label>"}]'
```

Each receipt accepts `topic_id` (the only required field), `status`, `channel`, `consumer`, `outcome`, `external_ref`,
and `agenda_date`. `status` is one of `shown` (default), `executed`, `dismissed`, `failed`; `channel` is one of
`in_conversation`, `inbox`, `notification`, `other` (default). Unrecognized values fall back to the default instead of
failing the call. Receipts are stored in the `deliveries` section of the `daily/_proactive.yaml` truth source and
trimmed by `retention_days` (180) and `max_deliveries` (500).

- **Identity**: `external_ref` wins when the host supplies one, otherwise `(topic_id, agenda_date, channel)`. Reporting
  the same delivery twice updates the record in place, so a host can report `shown` first and `executed` later.
- **Status only moves forward**: a terminal record (`executed`, `dismissed`) is never downgraded by a late `shown`, and
  `failed` does not block redelivery in the next round.
- **Two readers**: `proactive_step` withholds agenda items still inside `delivery_cooldown_days` (3), and
  `proactive_agenda_step` deterministically suppresses those candidates and writes an auditable reason into
  `suppressed`. `kind == "reminder"` is exempt from the cooldown on both sides — its `topic_id` derives from a stable
  schedule title, so normal suppression would silence a recurring reminder for the whole window after one delivery.
- **Optional contract**: a host that never reports leaves `deliveries` empty and both readers behave exactly as before.
  The step makes no LLM call and does not touch `open_topics`, `resolved`, or `schedules`.

Readers return the items they withheld as `delivered_ids`, in both the `answer` and the metadata, so a consumer can
reconcile them against its own local ledger.

## Running Proactive

### Start the Service and Read Topics

Start the service in one terminal and leave it running. The configured cron refreshes topics on schedule:

```bash
reme start config=default
```

From another terminal, read the generated topics:

```bash
reme proactive_read date=2026-06-20
```

Omit the raw YAML content:

```bash
reme proactive_read date=2026-06-20 include_content=false
```

### One-shot Refresh Without a Persistent Service

For maintenance or debugging that needs an immediate refresh, run the Job locally through the normal lifecycle:

```bash
reme start config=default job=proactive_refresh date=2026-06-20
```

`proactive_refresh` has `enable_serve: false`, so `reme proactive_refresh` cannot call it through a running service.
The local command may call the configured LLM and update `_proactive.yaml`, `interests.yaml`, and the proactive catalog.
It does not run Auto Dream. After it finishes, use the service-based read workflow above to retrieve the topics.

## Relationship to auto_dream

Proactive refresh and Auto Dream consume daily notes independently:

```text
daily notes -> auto_dream -> digest
daily notes -> proactive_refresh_cron -> daily/<date>/interests.yaml -> proactive_read -> host agent
```

The proactive responsibilities are divided as follows:

| Module                   | Responsibility                                         |
|--------------------------|--------------------------------------------------------|
| `proactive_refresh`      | Run the refresh pipeline once from the local CLI.       |
| `proactive_refresh_cron` | Run the same writer pipeline every day at 18:00.        |
| `proactive_step`         | Read `interests.yaml` and expose it to the host agent. |

`proactive_read` does not modify files, update a catalog, or decide whether the user should be interrupted. It only provides
the day's topic material. The caller's product policy determines whether, when, and in what tone to push it to the user.

## Failure Modes

| Scenario                            | Behavior                                               |
|-------------------------------------|--------------------------------------------------------|
| `interests.yaml` does not exist     | `success=true`, `skipped=true`, `topics=[]`.           |
| YAML cannot be read or parsed       | `success=false`; the answer contains an error summary. |
| YAML exists but has no valid topics | `success=true`, `topics=[]`.                           |

Callers should therefore check `success` first, then `skipped`, and finally whether `topics` is empty.
