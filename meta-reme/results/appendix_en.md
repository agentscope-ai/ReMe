# Appendix A: Case Studies of Memory System Optimization

This appendix summarizes memory design improvements from the BEAM and LongMemEval cleaned-S optimization runs, focusing on the failures they address and the mechanisms behind them.

## A.1 BEAM: Coverage, Order, and Access to Evidence in Long Conversations

1. **Reserve room for both curated memory and primary evidence in the retrieval window.** The system stores condensed notes alongside verbatim transcripts, which account for roughly 95% of indexed chunks. A window filled solely by the highest-scoring chunks is therefore easily dominated by transcripts, leaving out the notes that integrate information across passages. The optimized ranking favors notes while reserving slots for transcripts, so the answering agent can use the consolidated account and still check exact wording, numbers, and chronology. This rearrangement changes the order of candidates without discarding any. Crucially, it happens before the system marks returned chunks as seen: otherwise, a chunk displaced from the window could be recorded as already shown and become unreachable in later searches. In a mixed memory store, the *source composition of the window* matters as much as the ranking of individual chunks.

2. **Compress search responses without cutting off access to the original text.** Long transcript chunks make repeated searches expensive, yet a simple truncation can hide the line containing the answer. The first measure placed a character budget on responses while retaining the path and line range for each result; text that did not fit remained available through an explicit pointer for targeted reading. When truncation from the beginning repeatedly omitted facts in the middle or end of a note, selection moved to the line level. Lines were scored using the distinctiveness of query terms, numbers, and heading cues. The budget first covered multiple evidence-bearing lines, then used any remaining space for adjacent context. When a semantic match had no lexical overlap, the title and summary were still retained. Effective compression thus has two requirements: show the most useful evidence now, and make every omitted passage straightforward to locate later.

3. **Give coverage questions a global view instead of repeatedly enlarging top-k.** Answers to questions such as “Which topics did I mention?” may be spread across many sessions. Similarity search can return highly relevant chunks without establishing that all matching occurrences have been found. The optimizer therefore derived a compact chronological index from *all* notes, appended it to ordinary retrieval results, and delivered it automatically at most once per question. Entries carried paths for verification. Near-duplicate entries from overlapping notes in one session were consolidated while their paths remained accessible. To control cost, automatic delivery was routed only for coverage questions after offline checks. A measured regression exposed the index's limit: a thematic summary can look sufficient for a question about the *first-mention order* while omitting precisely the ordering evidence needed to answer it. A global index can support “what was mentioned” without automatically serving as an answer to “in what order.”

4. **For ordering questions, provide a reading route rather than a summary that invites an immediate answer.** Ordering evidence spans dates and sessions, so one note seldom contains all relevant mentions. An earlier summary-style index encouraged the agent to answer from its overview, saving tokens but getting the sequence wrong. The revised route listed note paths in chronological order and then annotated each path with the line range of its conversation-flow section. The agent could read the passages that recorded mention order and speaker identity without loading every entire note. Those sections occupied about 30% of a note on average, making broader coverage feasible within the tool and context budgets. An index need only guide reading; when the answer depends on fine-grained order, compressing evidence into a topical summary can remove the deciding information.

5. **Record relationships at construction time that retrieval cannot reconstruct.** Case-level traces showed failures in which the relevant note had been found, but the note never preserved *who* made a statement, *when* a topic first appeared, or whether a new statement superseded an older one. Construction rules were revised to identify the speaker, distinguish an assistant's suggestion from a user's decision, retain a conversation-flow record in actual mention order, preserve enduring instructions verbatim, and keep both sides of an update with an explicit supersession relation. Retrieval can reorder stored text; it cannot recover attribution, order, or update relations discarded during compression. The questions a memory system must answer should therefore inform the structure of what it writes.

## A.2 LongMemEval cleaned-S: Fact Recall, Aggregate Retrieval, and Answer Calibration

1. **Write short, self-contained user facts instead of topic-oriented essays.** Baseline notes often devoted space to generic advice while losing exact dates, numbers, or the option the user actually chose. The surrounding generic text also diluted the embedding representation of specific facts. The revised construction policy prioritized complete user states, preferences, decisions, and feelings; preserved session-specific names, dates, and prices verbatim; and compressed generic explanations to a line. It aimed for one note per session, beginning with self-contained key user facts. This reduced overlapping notes and made important facts more likely to survive chunking and be retrieved on their own. When a length budget is tight, generic background should be removed before user facts.

2. **Control both semantic duplication and concentration by source in a small window.** Similar notes from one session can consume nearly every retrieval slot. Multiple chunks from one transcript can also occupy several slots before rendering merges them into a single displayed item, leaving no room for a different source. The first problem was addressed with relevance-heavy maximal marginal relevance: highly similar candidates receive a modest penalty while strong retrieval scores still dominate. The second was addressed by capping the slots taken by each file, with a stricter cap for raw transcripts than for notes. Both mechanisms postpone excess candidates rather than deleting them. The useful accounting unit is the *distinct evidence ultimately delivered*, not merely the number of retrieved chunks.

3. **Add an inexpensive catalog index beyond top-k retrieval.** A question such as “How many times did I attend a graduation?” requires every occurrence, whereas a similarity search guarantees only the most similar few. Each note already has a title and a one-line description, so the system can scan this compact catalog across all notes, match query terms, and append a candidate list to normal search results. A document-frequency threshold removes generic template words such as “user”; ranking uses the strongest discriminative term rather than allowing many weak matches to accumulate. Each entry keeps its path and a description excerpt around the match, telling the agent which note to inspect. The index addresses a *coverage gap* in top-k retrieval while leaving semantic search in place.

4. **Extend the catalog to individual facts while retaining both levels.** A one-line description is necessarily lossy: an additional graduation, a particular island, or a precise bedtime may appear only in the note body. The expanded index scans notes and splits self-contained Markdown list items into fact entries. Matching entries are quoted inline, allowing the agent to use the fact without another read call. Fact and catalog layers calculate term frequencies and rankings separately, so adding the finer layer does not silently change how the coarser one behaves. Facts already visible in the normal retrieval window are suppressed in the index to avoid duplication. The catalog remains useful because a question phrased in terms of a session's topic may share no content word with the answer sentence. The layers answer complementary questions: “Which note might matter?” and “Which statement in it matters?”

5. **Keep the inexpensive index available, vary its width, and state what a match proves.** The run briefly gated index delivery to enumeration questions or explicit requests to reduce irrelevant matches. Case-by-case inspection showed that the gate did not cause the improvements initially attributed to it; withholding the index instead prompted repeated blind query rewrites and higher total token use. The final design kept the index available for every question, returned a shorter list for point queries and a wider one for enumeration, and warned in the index header that keyword overlap is only a lead. A nonempty list does not establish that the entity or event in the question exists; each entry must be checked against the requested fact. Query wording alone did not predict where evidence was stored. For a cheap index, controlling output size and clarifying evidential meaning proved more useful than gating access by question form.

6. **Diagnose “the evidence was found” separately from “the answer was correct.”** In several cases the agent read the right note but abstained because it demanded a completion confirmation that memory would never record. In others, it corrected a false premise yet still supplied the value that the false premise requested. Answering rules were calibrated to anchor relative times, use newer records for current state, respect entity boundaries, and reject the requested value when its premise is false. Rules without case-level evidence were later removed because their prompt cost recurred at every ReAct step. A memory answer can fail at construction, retrieval, evidence interpretation, or final decision. More retrieved material is unlikely to repair a decision error once the correct evidence is already visible.

Together, these runs show that memory optimization reaches beyond vector ranking. Construction determines which relationships remain recoverable; the retrieval window determines which sources fit within a budget; derived indexes address the coverage limits of top-k search; and answer policy determines how evidence is used. When validation rounds sample different cases, contributions of individual mechanisms are best assessed through paired questions and execution traces, particularly when several changes were introduced together.
